## 문제 프레임

QA 리드로 발탁된 직후 세운 첫 목표는 **팀원의 성과를 상향 평준화하는 것**이었습니다.
배포된 Test Checklist 생성 프로세스가 Legacy가 된 상황이었고, 로컬 LLM 사용에 따른 실효성이 떨어졌기에, **사람이 진행한 테스트를 고성능 LLM이 평가할 수 있도록 해보는 것**이 목표가 되어 진행했던 프로젝트였습니다.
큰 원동력은 Hermes가 실제 '오케스트레이터 및 웹훅' 역할이 가능하다는 점.
Hermes 내부의 Claude Code 활용이 API 종량제 호출 외 사용이 가능하다는 점이 있었습니다.

## 설계

### ced-taker

후에 소개될 **프로젝트④**에서 User 개인이 작성한 **Context Enrichment Docs(이하 CED)**를
Hermes - Obsidian Vault 측에 구축하고, 이것을 분석 전 **'참조 문서'**로 제공합니다.
재직 중 Legacy가 된 Test Checklist 생성 자동화는 '테스트의 경중을 모른다.', '맥락을 모른다.'
두 개의 큰 이슈가 있었고, **큰 프로젝트에서 자동 생성된 문서는 신뢰가 불가능한 단순 참조 문서였습니다.**
ced taker로 하여금 **이런 이슈를 해결**합니다.
Test에 필요한 맥락 문서를 LLM에게 줄 수 있는 캐시 저장, 전송 역할로 설계되었습니다.

(프로젝트④: DBViewer-tagger, https://github.com/wonderwall1995/dbviewer-tagger)

### controller

Hermes 내부의 **프로젝트들이 서로를 몰라야 한다는 의도로 만들어진 중간 허브(hub)**입니다.
에이전트 내부의 프로젝트들을 잇고, **프로젝트가 서로 독립성을 갖게끔 만드는 의도**입니다.
향후 API 테스트 코드를 자동으로 생성하게끔 맡겨 본다든가 하는 구상이 있습니다.
ced-taker와 test-gate가 다른 프로젝트에서 인용될 수 있게 미리 만들어둔 중간 다리 프로젝트입니다.

### test-gate

github-app이 가져온 Diff를 분석합니다. Claude Code를 호출하는 기능이 있습니다.
GitHub의 Pull Request 측 코멘트를 기억하고, 작성하고, 수정하는 역할을 겸하고 있습니다.
테스트에 대한 보고서 / 테스트 커버리지 충족 여부에 대한 조언, 그와 같은 내용을 HTML로도 제공하고 있습니다.

## 아쉬운 점

이전 재직 중이던 회사에서 기획하고 구현을 앞두고 있었으나, 퇴사를 결정하면서 생긴 문제는
실제로 본 프로젝트가 얼마나 효용 가치를 지녔는지 정성적인 성과, 정량적인 평가가 없다는 점입니다.
**다수의 User 대상으로 라이브 서비스 중인 제품 대상으로 적용해본 적이 없다는 점**이 가장 아쉽습니다.

# hermes-ced-taker

사람이 확인해 적어 둔 **DB 컬럼의 뜻**을, 코드와 PR만 봐서는 알 수 없는 용어를 해석해야 하는 AI 에이전트가 쓸 수 있게 하는 공통 계층이다.

> 초기 단계이다. 아래에서 "한다"는 목표이고, 지금 되는 것과 아닌 것은 [지금 상태](#지금-상태)에 따로 적었다.

## 왜 만드는가

코드나 PR의 diff에는 `balance`, `status` 같은 이름이 나온다. 이름만으로는 뜻을 알 수 없다. 같은 이름이 테이블마다 다른 뜻일 수도 있다. AI가 이를 추측하면 곡해한다.

그래서 DB의 컬럼마다 사람이 뜻을 확인해 적은 문서(CED, Context Enrichment Docs)를 만든다. 이 프로젝트는 그 문서를 받아서, 필요한 순간에 필요한 만큼만 AI에게 건네는 일을 맡는다.

## 무엇을 위해 무엇이 있는가

| 구성 | 무엇을 위한 것인가 |
|---|---|
| 받는 곳 | CED를 만드는 앱이 보낸 문서를 믿을 수 있게 받는다. 온전히 도착한 문서와 중간 상태의 문서를 구분한다. |
| 기억하는 곳 | 받은 문서를 찾기 쉬운 형태로 기억한다. 원문은 고치지 않는다. 기억은 언제든 원문에서 다시 만들 수 있다. |
| 골라 주는 곳 | PR의 diff와 설명에서 컬럼 이름을 찾아, 관련 문서만 짧게 골라 건넨다. 전부 읽게 하지 않는다. |

## 우리는 이것을 어떻게 할 것인가

- **컬럼 이름이 열쇠이다.** 컬럼 이름이 곧 문서 이름이다. 이름이 정확히 같을 때만 문서를 찾는다. 비슷하지만 못 찾은 경우는 기록해서, 규칙을 넓힐지 데이터로 정한다.
- **AI의 토큰을 쓰지 않는다.** 찾고 고르고 줄이는 일은 코드가 한다. AI는 이미 골라진 짧은 해설만 받는다.
- **넘치면 버리지 않고 줄인다.** 관련 문서가 많으면 중요한 것은 전체를, 나머지는 한 줄로, 그 밖에는 개수만 알린다.
- **원문은 건드리지 않는다.** 이 프로젝트는 문서를 읽기만 한다. 깨졌거나 수정된 문서는 쓰지 않고, 이전의 정상 내용을 쓰며, 그 사실을 알린다.
- **하나의 하위 프로젝트에 묶지 않는다.** 특정 프로젝트 전용이 아니다. 어떤 프로젝트든, 어떤 업무든 같은 방식으로 쓸 수 있어야 한다.
- **Hermes가 쓰게 하는 것이 최종 목표이다.** 이 프로젝트와 다른 프로젝트는 서로를 모른다. Hermes가 둘을 알맞은 순서와 의도대로 쓰게 하는 것을 기획한다.

## 하지 않는 것

- 문서를 만들거나 고치지 않는다. 문서는 송신하는 앱의 몫이다.
- DB의 실제 값(행)을 다루지 않는다. 컬럼의 뜻만 다룬다.
- 뜻을 AI가 추측해서 채우지 않는다. 사람이 확인한 문서만 쓴다.
- 개인 정보, 접속 정보, 실제 문서 내용을 저장소에 넣지 않는다.

## 지금 상태

**되는 것**
- 문서를 읽어 구조(제품, 키워드, 위치, 본문)로 바꾼다.
- 도착한 문서가 온전한지 해시로 검증한다.
- 검증된 문서를 DB에 반영한다. 바뀐 문서는 갱신하고, 사라진 문서는 비활성으로 표시한다.
- diff와 PR 설명에서 컬럼 이름을 찾아 해설 문단을 만든다.
- 다른 프로그램이 명령으로 불러 쓸 수 있다. 표준 입력의 JSON 요청에 JSON으로 답하는 약속(참고 문서 공급자)을 지킨다. 어떤 프로그램이 부르는지는 모른다.

**아직 안 되는 것**
- 실제 환경에서의 연결. 부르는 쪽(hermes-controller)과 함께 시험했지만, 실제 PR로의 시험은 하지 않았다.
- 한국어와 영어가 섞인 이름의 폭넓은 대응. 지금은 정확히 같은 이름만 찾는다.
- 사람이 읽는 노트 쓰기.
- 문서를 보내는 앱 쪽의 변경(목차 파일명 분리 등). 요청문은 만들었지만 아직 반영되지 않았다.

## 예시

[examples/](examples/)에서 결과를 바로 볼 수 있다. 데모 볼트(`demo-vault/`)의 문서로 만든 것이다.

| 파일 | 무엇인가 |
|---|---|
| `demo-vault/CED/` | 송신하는 쪽이 보낸 문서의 예. 상태 파일의 해시와 함께 있다. |
| `demo.db` | 데모 볼트에서 만든 DB. 한 파일이고 열어 볼 수 있다. |
| `schema.sql` | DB의 표 구조. 코드에서 만든 DB에서 읽어 낸 것이다. |
| `sample.diff`, `sample-description.txt` | 입력의 예. 락 파일의 변경도 들어 있다. |
| `explain-example.md` | 위 입력에서 만든 해설. 락 파일의 단어는 빠지고, "balance를"처럼 조사가 붙은 단어도 찾는다. |
| `provide-request.json`, `provide-response.json` | 다른 프로그램이 명령으로 부를 때 주고받는 약속의 예. [contracts/](contracts/)의 사본과 같다(원본은 hermes-controller). |

`python3 scripts/build_demo.py`(또는 `pnpm demo:build`)가 생성 파일을 다시 만들고, 시험이 올려 둔 파일과 지금 코드가 만든 결과가 같은지 확인한다. DB는 볼트에서 다시 만들 수 있는 캐시이므로 실제 운영 중인 DB는 올리지 않고, 데모 볼트로 만든 DB만 올린다.
