# 11-18 설정 기록: 질문과 합의의 과정

기간: 2026-11-17 ~ 11-18

이 문서는 설계 의도를 남긴다. 나중에 "잘못된 선택"을 알아보고, 되돌리고, 새로 설계하기 쉽게 하는 것이 목적이다.

## 읽는 법

- 이 문서는 대화의 요약이다. 선택지 문구는 뜻을 지키며 줄였다.
- **선택** = 사용자가 고른 것. **제안** = Claude가 권한 것.
- **권장안과 다름** = 사용자가 Claude의 권장안 대신 다른 것을 골랐다. 되돌릴 후보를 찾을 때 먼저 본다.
- **추정** = 검증하지 않은 가정이다. 5장에 모았다.
- 개인 정보와 환경 정보는 쓰지 않았다. 예시 제품은 "제품 A"로 적는다.

## 2. 결정 기록 (시간순)

### D01 첫 소비자

- 질문: CED를 가장 먼저 쓸 대상은 누구인가?
- 선택지: testgate(권장) / Hermes 대화 / Claude Code와 Codex / 공통 계층만 먼저
- 선택: 공통 계층만 먼저. 권장안과 다름.
- 이유: 선택할 때는 말하지 않았다. 나중에 D24에서 "범용 프로젝트"라는 의도가 밝혀졌다. 같은 방향이다.
- 되돌리면: 코드는 영향이 없다. testgate 연동은 Backlogs에 있다.

### D02 과거 CED

- 질문: 이전에 만든 CED는 어떤 상태인가?
- 선택지: 한 제품뿐(권장) / 송신 앱에 더 있음 / 볼트의 다른 곳에도 있음
- 선택: 한 제품뿐. 소급 처리 기능은 만들지 않았다.
- 되돌리면: `sync_vault`가 모든 제품 폴더를 한 번에 처리한다. 그래서 문서가 한꺼번에 와도 동작한다. 볼트 밖의 옛 문서는 처리하지 못한다.

### D03 CED를 외부 AI에 보내도 되는가

- 처음 질문은 어려웠다. 사용자는 이해하지 못했다고 답했다. 쉬운 말로 다시 물었다.
- 선택지: 허용(권장) / 제품마다 사용자가 정함 / 허용 안 함
- 선택: 허용.
- 이유: CED는 DB 값이 아니라 컬럼의 뜻을 적은 문서이다.
- 되돌리면: 제품별 허용 표시 기능이 필요하다. 아직 없다.

### D04 두 AI 도구의 작업 방식

- 선택지: 역할 분담(권장) / 작업 폴더 분리 / 번갈아 작업
- 선택: 선택지 밖의 방식. 두 도구를 번갈아 쓴다. 할당량이 끝나면 다른 도구로 넘어간다. 작업을 마칠 때 도구별로 인계 문서를 쓴다.
- 이유: 할당량 문제가 크다.
- 되돌리면: 두 도구가 동시에 같은 파일을 고치려면 충돌 규칙이 필요하다.

### D05 인계 문서의 위치

- 질문: 공개 저장소인데 인계 문서를 어디에 두는가?
- 선택: 사용자가 직접 전달한다. 저장소에 두지 않는다.
- 이유: 선택할 때는 말하지 않았다. 질문에서 제시한 위험은 개인 정보 노출이었다.

### D06 스택과 시험 도구

- `pnpm init`을 먼저 지시받아 실행했다. 이후 사용자가 언어를 Python으로 정했다. testgate와 비슷하면 충분하다고 했다.
- testgate를 확인한 결과: Python 3.14 표준 라이브러리만 쓰고, unittest로 시험하고, pnpm은 명령 단축에만 쓴다.
- 시험 도구는 사용자가 추천을 요청했다. 제안: unittest. 이유는 설치할 것이 없고, testgate와 같아서 인계가 쉽고, 임시 폴더로 볼트를 흉내 내기 쉽다는 것이다. 사용자는 이의가 없었다.
- 정리: `pnpm init`으로 만든 `package.json`은 명령 단축용으로 남겼다.
- 되돌리면: pytest로 바꾸면 의존성이 하나 늘어난다.

### D07 Git 제외 항목

- 선택: 빌드 결과물, 에디터 설정, `local/` 폴더. 색인과 DB는 고르지 않았다. 이유는 말하지 않았다. 이후 DB를 저장소 밖에 두기로 했다(D11).

### D08 수신 감지

- 사용자 아이디어 1: 송신 쪽이 보내는 특정 요청을 훅으로 이해시킨다.
- 제안: 훅은 "지금 확인하라"는 초인종으로만 쓴다. 도착 여부는 항상 상태 파일의 해시로 판단한다. 훅은 유실될 수 있기 때문이다.
- 사용자 아이디어 2: DB의 문을 두드리면 Hermes가 알아서 사전을 뒤진다.
- 제안: 조회 함수가 DB를 뒤지기 직전에 먼저 동기화한다. 상시 서비스, 파일 감시, 훅이 모두 필요 없고, 송신 앱을 고칠 필요도 없다.
- 선택: 조회 직전 동기화(권장). 훅 즉시 처리는 Backlogs에 있다. 상시 서비스는 아직 기록하지 않았다.
- 되돌리면: 감시 모듈을 추가하고 `sync_product`를 재사용한다.

### D09 저장 방식

- 사용자는 이 프로젝트 자체의 DB를 둔다는 점에 흥미를 보였다. 선택: SQLite.
- 파일에서 매번 읽는 방식과 JSON 파일 방식도 제시했다.

### D10 소비 방식

- 사용자 요구: Hermes 세션의 토큰을 쓰지 않는 방향. PR의 모호한 용어를 CED로 해석하게 한다.
- 제안: 코드가 diff에서 단어를 찾아 해설 문단을 만들어 분석 프롬프트에 주입한다. 이 경로에는 Hermes 세션이 없다. testgate 문서에 따르면 Hermes 세션은 분석 경로에 없고 거부할 수도 있기 때문이다.
- Claude Code가 직접 조회하는 방식은 도구 권한 검토가 필요해서 미착수이다.

### D11 DB와 노트의 위치

- 사용자 원안: 볼트 안을 우선한다. 볼트는 저장소처럼, Hermes는 힙 메모리나 메모리 카드처럼 쓴다.
- 제안: DB는 Hermes 폴더에 두고, 사람이 읽을 노트는 볼트의 CED 밖 별도 폴더에 쓴다.
- 이유: (1) 동기화 도구가 열려 있는 DB 파일을 복사하면 깨질 수 있다. (2) CED 폴더는 송신 앱이 소유한다. (3) DB는 다시 만들 수 있는 캐시라서 저장소에 둘 이유가 없다. (4) Hermes 자체 메모리는 2,200자 한도라 CED를 담을 수 없다. "힙"은 필요한 항목만 그때그때 올리는 방식으로 이해했다.
- 선택: 제안대로.
- 되돌리면: `CED_TAKER_DB`로 DB 위치를 바꿀 수 있다. 볼트 안에 두려면 동기화 도구와의 충돌을 먼저 확인해야 한다. 사람용 노트 쓰기는 아직 구현하지 않았다.

### D12 이름 일치 규칙

- 선택지: 정확 일치 + 놓침 기록(권장) / 대소문자 무시 / 대소문자와 snake·camel 통일
- 선택: 정확 일치. 비슷하지만 못 찾은 경우는 `misses` 표에 기록한다.
- 이유: 사용자가 정확 일치만으로 잘 해내면 된다고 보았다. 기록은 나중에 모양 통일이 필요한지 데이터로 판단하기 위한 것이다.
- 되돌리면: `funnel.py`의 `find_matches`에 정규화 비교를 추가한다. 놓침 기록이 근거가 된다.

### D13 목차와 Key의 이름 충돌 (미결)

- 문제: 파일명이 컬럼명이다. 제품 이름과 같은 컬럼이 있으면 목차(`<제품>.md`)와 Key 문서의 파일명이 같아진다. 한 폴더에서 한쪽이 다른 쪽을 덮어쓴다.
- 수신 쪽에서는 해결할 수 없다. 덮어써진 내용은 이미 사라진다.
- 사용자는 역제안을 요청했다. 제안: 수신 쪽은 문서 형식으로 구분하고, 충돌이 보이면 오류로 기록한다. 송신 앱에는 세 가지를 요청한다. (1) 목차 파일명을 `_<제품>.md` 같은 예약 이름으로 바꾼다. (2) front matter에 `type`을 넣는다. (3) 컬럼 뜻을 테이블별로 구조화한다.
- 상태: 요청문을 대화로 제공했다. 전달 여부는 확인하지 못했고, 송신 앱은 아직 바뀌지 않았다.

### D14 질문 방식

- 사용자는 질문을 질문 GUI(AskUserQuestion)로 하는 것을 기본 작업 방식으로 정했다. 선택형이 텍스트 질문보다 빠르다는 이유이다.
- 이 규칙은 Claude Code의 기억에만 저장됐다. Codex에는 전달되지 않으므로 인계 문서에 적어야 한다.

### D15 LLMS.md 수정 허락

- 선택: To-do와 Backlogs에 항목을 한 줄씩 넣는 것을 허락했다. Done과 진행 상태 라벨은 아직 허락받지 않았다.

### D21 깔때기의 입구와 출구

- 사용자는 문서를 날것으로 전부 읽는 대신 "중화"하는 깔때기가 필요하다고 했다. 출구의 상한이 적당한지도 물었다.
- 제안: 상한은 평소에는 닿지 않는 안전장치이다. 실제 문서 1개는 약 800바이트이다. 더 중요한 거름은 입구에 있다.
- 사용자는 넘친 문서를 "영리하게 무효화"하라고 했다. 제안: 버리지 않고 단계적으로 줄인다.
- 선택: 3단계 출구(상위 5개는 본문 전체, 다음 30개는 한 줄 카드, 나머지는 개수만). 입구는 바뀐 줄과 PR 설명만 본다.
- 주의: 5와 30은 근거가 약하다. 문서 1개의 크기에서 추정한 값이고, 토큰 길이는 측정하지 않았다. 설정으로 바꿀 수 있다.
- 되돌리면: `funnel.Limits`의 값을 바꾼다.

### D22 약한 열쇠 규칙 (D23이 대체)

- 선택: 강한 열쇠와 함께 걸릴 때만(권장).
- 이 선택은 D23으로 대체됐다. 구현하지 않았다.

### D23 열쇠는 컬럼명 하나

- 사용자 정정: 테이블 이름은 중요하지 않다. 컬럼명이 곧 파일명이고, 파일이 곧 Hermes가 쓸 CED 문서이다.
- 제안: 찾기는 컬럼명 정확 일치만 쓴다. 테이블과 키워드는 DB에 저장하지만 첫 버전에서는 찾는 데 쓰지 않는다. 뜻이 여럿인 컬럼(예: 한 컬럼이 두 테이블에서 다른 뜻을 가짐)은 문서 전체와 `appearsIn`을 보여 주고 Claude가 diff의 맥락으로 고르게 한다.
- 이 정정 전에 사용자가 고른 순위 규칙("정확한 위치 우선")도 바뀌었다. 선택: 걸린 횟수가 많은 순, 동점이면 `테이블.컬럼` 위치가 맞는 문서가 먼저(권장).
- 되돌리면: `find_matches`를 확장한다. 키워드와 테이블 열쇠는 이미 저장돼 있다.

### D24 범용성 (설계 미착수)

- 사용자 의도: 이 프로젝트는 hermes-test-gate에 쓰게 만드는 것이 목적이 아니다. hermes-test-gate와 완전히 독립된 프로젝트이다. Hermes 자체가 두 프로젝트를 정확히 알맞은 순번과 의도대로 쓰게 하는 것을 기획한다.
- 반영: `LLMS.md`의 Rules 마지막 줄과 To-do 9번.
- 상태: 이 결정은 지금까지의 코드에 이미 반영돼 있다. `explain`은 testgate를 모르고, 입력은 diff 텍스트와 PR 설명 텍스트뿐이다. Hermes가 두 프로젝트를 쓰게 하는 부분은 설계하지 않았다.

## 4. 구현 중 발견한 결함

설계 결정에 영향을 줄 수 있는 것만 적는다.

- **특수 파일**: 상태 파일이 디렉터리나 FIFO를 가리키면 중단되거나 영원히 멈출 수 있었다. 열기 전에 파일 종류를 확인하고 일반 파일만 읽도록 고쳤다.
- **약한 시험**: 저장 중 실패해도 부분 데이터가 남지 않는다는 시험이 처음에는 트랜잭션 없이도 통과했다. 마지막 단계에서 실패하도록 고쳤다.
- **한국어 조사**: PR 설명의 "balance를", "balance가"가 한 단어로 읽혀서 `balance` 문서를 놓쳤다. 영문 식별자와 한글을 따로 자르도록 고쳤다. D12의 "정확 일치"는 단어를 어떻게 자르는가에 달려 있다는 뜻이다.
- **검증 방식**: 핵심 보호 장치를 일부러 깨 보고 시험이 실패하는지 확인했다. 시험이 통과하는 것만으로는 시험이 약한지 알 수 없기 때문이다.

## 6. 되돌리는 방법

| 결정 | 건드릴 곳 | 방법과 주의 |
|---|---|---|
| D01, D24 | 문서만 | 코드는 소비자를 모른다. 연동은 새로 설계한다. |
| D08 | `sync.py` | 감시 모듈을 만들어 `sync_product`를 부른다. 조회 직전 동기화는 유지해도 된다. |

| D12, D23 | `funnel.py`의 `find_matches` | 정규화나 테이블·키워드 열쇠를 추가한다. 저장된 열쇠를 그대로 쓴다. |

| D19 | `store.py` | 스키마를 바꾸면 `SCHEMA_VERSION`을 올린다. DB는 캐시라 지우고 `sync`로 복원한다. 이력과 놓침 기록은 복원되지 않는다. |
| D21 | `funnel.Limits` | 상한 숫자를 바꾼다. |
| D26 | `funnel.Limits.excludes` | 빈 목록으로 두면 호출하는 쪽의 규칙만 쓴다. |
