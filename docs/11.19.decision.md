## 1. 사용자가 그린 그림과 지금 구현

사용자가 원하는 그림:

```
github-app (공급자) → Hermes (오케스트레이터) → ced-taker (컨설팅) → testgate (분석자)
```

지금 구현된 모양(소스를 읽어 확인함):

```
github-app → Hermes 웹훅 → testgate의 필터 → testgate의 래퍼 → testgate의 분석
                                                              └─ 분석 도중 testgate가 ced-taker를 부른다
```

**차이는 하나이다.** 지금은 ced-taker를 부르는 쪽이 Hermes가 아니라 testgate이다. Hermes의 웹훅은 testgate의 필터 스크립트 이름만 알고 있다. 그림대로라면 Hermes 쪽이 "ced-taker를 먼저, 그다음 testgate" 순서를 정해야 한다. 이것이 결정 1이다.

## 2. 헷갈린 말 두 개

- **문서**: 송신 앱이 만든 컬럼 설명 파일 하나이다(예: `balance.md`). ced-taker가 읽어서 DB에 넣는 단위이다.
- **문서 ID**: ced-taker가 testgate에 건네는 꾸러미의 항목마다 붙이는 내부 이름표이다(예: `ced:balance`). testgate가 여러 참고 자료를 구별하려고 쓴다. 사용자가 정할 일이 아니다. 앞서 이것을 질문한 것은 내부 규칙을 사용자에게 물은 잘못이었고, 질문을 거둔다. 사용자가 이미 한 답("제품이 여러 개일 때만 제품 이름을 넣는다")을 구현 때 따른다.

## 3. 이미 정해진 것 (다시 묻지 않는다)

- 기본은 **모든 저장소가 모든 CED 제품의 컬럼을 참조**한다. 설정으로 저장소를 특정 제품들로 **제한**할 수 있다. 제외 설정은 두지 않는다.
- ced-taker에 볼트 설정이 없으면 **오류**로 한다.
- 제품 이름은 내부 이름표에 **제품이 여러 개일 때만** 넣는다.
- 서버나 Hermes 폴더에 설치하는 일은 testgate의 몫이다. ced-taker는 설치가 없다.
- 실제 PR로 하는 시험은 나중에 한다.
- github-app에 "저장소가 CED 용어를 갖는지 알아보는 API"를 더하는 아이디어는 지금 하지 않는다.
- 포트폴리오용으로 데모 볼트(실제 문서 그대로)로 만든 DB를 올린다. 이미 커밋돼 있고 푸시는 하지 않았다.

## 4. 결정할 것 (프로젝트별)

### 전체 (Hermes)

**결정 1. ced-taker → testgate 순서를 누가 정하는가?**

| 선택지 | 모양 | 상태와 비용 |
|---|---|---|
| **(가) testgate가 부른다** | testgate의 설정 한 줄이 ced-taker 명령을 가리킨다. Hermes는 변경이 없다. | **이미 만들어져 있고 시험까지 끝났다.** testgate는 ced-taker 이름은 모르고 명령만 안다. |
| **(나) Hermes가 부른다** (사용자의 그림) | Hermes 쪽의 중립 스크립트가 ced-taker를 먼저 실행하고, 그 결과를 testgate의 입력으로 넘긴다. testgate는 ced-taker가 있는지도 모르고 "추가 참고 자료"만 받는다. | 아직 없다. 새로 만들 것: Hermes 쪽 연결 스크립트, testgate가 참고 자료를 받는 방식 변경, **웹훅 라우트가 가리키는 스크립트 교체(라이브 변경)**. |

- **내 의견**: 그림에 맞는 것은 (나)이다. 다만 (나)로 가도 ced-taker 쪽에서 만든 것(`provide` 명령, 계약, 시험)은 그대로 쓴다. Hermes 쪽 스크립트가 같은 명령을 부르면 되기 때문이다. 달라지는 것은 testgate 쪽 코드이다.
- **가장 중요한 이유**: 사용자의 두 요구, "프로젝트가 서로를 직접 모른다"와 "Hermes가 순서를 정한다"를 모두 만족하는 것은 (나)이다. (가)는 앞의 것만 만족한다. testgate가 순서를 정하고 있기 때문이다.
- (나)를 고르면 **결정 1-1**이 따라온다: Hermes 쪽 연결 스크립트를 어느 저장소가 갖는가(새 저장소 / ced-taker의 폴더 / testgate). 이 질문은 (나)일 때만 한다.

### github-app

**결정 없음.** 지금 하는 일(PR 데이터를 공급)을 바꾸지 않는다. 3장에 적었듯 저장소 정보 API는 하지 않는다.

### ced-taker

**결정 2. 같은 컬럼명이 여러 제품에 있으면(예: `balance`) 어떻게 보여 줄까?**

- 사용자 의견: 같은 컬럼명은 송신 앱이 문서 하나로 합치고 "뜻이 둘"이라고 적는 쪽으로 가는 것이 맞다.
- 그 변경이 반영되기 전까지의 ced-taker 동작을 정해야 한다.
- 선택지: (가) 둘 다 보여 준다(제품 이름을 붙여 구분) / (나) 하나만 보여 준다.
- **내 의견**: (가). (나)는 어느 쪽을 고를지 임의라서 뜻이 빠질 수 있다.

**결정 3. ced-taker의 "기본은 전체 참조, 선택은 제한" 변경은 언제 구현하는가?**

- 이 변경은 결정 1이 (가)든 (나)든 필요하다. 지금 코드는 "저장소를 등록해야 동작"이라서 의도와 반대이다.
- 선택지: (가) 결정 1을 정한 뒤에 한다 / (나) 결정 1과 상관없으니 먼저 한다.
- **내 의견**: (가). 사용자가 맥락을 놓치고 있는 지금은 결정을 먼저 정리하는 쪽이 낫다. 변경 자체는 작다.

### testgate

**결정 4. 이미 만든 변경은 어떻게 하는가?**

- 브랜치 `feat/context-providers`에 커밋 3개가 있다(공급자 자리 추가, 안내 문서, `FilterSpoolTest` 수정). `main`은 건드리지 않았고 푸시도 하지 않았다.
- 선택지: (가) 결정 1이 정해질 때까지 그대로 둔다 / (나) 결정 1이 (나)로 정해지면 공급자 자리 부분을 정리한다.
- `FilterSpoolTest` 수정(커밋 `b3456ea`)은 공급자와 무관하게 독립이라, 떼어서 먼저 병합할 수 있다.
- **내 의견**: (가). 병합은 PR로 해야 하고 푸시가 필요하므로, 언제 할지는 사용자가 정한다.

### Hermes (이 컴퓨터의 로컬 Hermes)

**결정 5. 라이브에 반영하는 순서와 시점은?**

- 순서: 결정 1 → 구현 → testgate 설치 → 설정 파일 변경 → 실제 PR 시험.
- 지금은 모두 보류이다. 설치는 testgate의 몫이다.
- 사용자가 정할 것은 "언제 시작할지" 하나이다.
- 참고: 결정 1이 (나)이면 웹훅 라우트(`webhook_subscriptions.json`)가 바뀐다. 이것은 Hermes의 설정이라 신중해야 한다.

**결정 6 (급하지 않음). Hermes 업데이트 뒤에 확인할 것을 문서로 남길까?**

- 내용은 한 줄이다: testgate 저장소에서 `pnpm filter:check`를 돌려 "원본과 설치본이 같다"를 본다.
- `hermes update` 전체가 `~/.hermes/scripts`와 `testgate`를 건드리는지는 확인하지 못했다.

## 5. 앞서 질문 없이 정하거나 어긋나게 한 것 (되돌릴 후보)

사용자가 맥락을 놓친 원인이다. 숨기지 않고 적는다.

- **의도와 반대로 만든 것**: ced-taker의 "저장소를 제품에 연결해야 동작한다"와 "연결 없는 저장소는 조용히 빈 결과"(11-19 설계 기록의 D35, D42). 오늘 확인한 의도는 반대(기본이 전체)이다. 결정 3에서 고친다.
- **질문 없이 정한 구현 판단 11개**: 설계 기록(`11-19-provider-design.md`) 6장에 있다. 한 번에 읽기 어려운 양이었다.
- **허락의 범위를 넓게 해석한 것**: `LLMS.md`에 진행 라벨과 To-do 10~14번을 넣은 것.
- **범위가 컸던 것**: 두 프로젝트를 모두 구현하는 선택(D32)은 사용자가 했지만, 그 결과로 testgate 브랜치, 데모 예시, 설계 문서가 한꺼번에 생겼다.
- **내 일하는 방식을 바꾼다**: 앞으로 사용자가 말한 것만 하고, 대화에서 언급된 후속 일은 실행하지 않고 목록으로만 제안한다.
