# 11-19 참고 문서 공급자 설계: 두 프로젝트를 잇는 방법

기간: 2026-11-19

To-do 9번("Hermes가 두 프로젝트를 알맞은 순번과 의도대로 쓰게 한다")의 설계와 구현을 기록한다. 11-18 기록(`11-18-setup.md`)과 같은 목적이다. 나중에 잘못된 선택을 알아보고 되돌리기 쉽게 한다.

## 읽는 법

- **선택** = 사용자가 고른 것. **제안** = Claude가 권한 것.
- **권장안과 다름** = 사용자가 Claude의 권장안 대신 다른 것을 골랐다.
- **구현자 판단** = 질문하지 않고 구현 중에 정한 것. 6장에 따로 모았다. 되돌리거나 다시 물을 후보이다.
- **추정** = 검증하지 않은 가정이다. 8장에 모았다.
- 개인 정보와 환경 정보는 쓰지 않았다. 예시 저장소는 `acme/shop`, 예시 제품은 "제품 A"이다.

## 2. 출발점: 실제로 확인한 사실

설계 전에 Hermes와 testgate를 읽기 전용으로 확인했다. 이 사실들이 선택지의 모양을 정했다.

1. **순서를 정하는 것은 코드이다.** testgate의 분석 경로는 웹훅 수신기, 필터, 래퍼, Claude 순이다. Hermes 세션의 LLM은 이 경로에 없고, 요청의 기록만 남기며 거부하는 일도 있다. 그래서 "LLM이 안내 문서를 보고 순서를 지키게 한다"는 방식은 선택지에서 기각됐다.
2. **testgate에는 이미 끼울 자리가 있다.** 참고 문서 공급자(`knowledge.load(context)`)가 `{id, title, text}` 목록을 돌려주는 모양이다. 문서는 신뢰하지 않는 데이터 블록으로 프롬프트에 들어간다. 지금까지는 폴더의 파일을 전부 읽을 뿐 어떤 PR에 어떤 문서가 맞는지는 가리지 않았다.
3. **Hermes의 훅은 세션 생명주기용이다.** 게이트웨이 시작, 세션 시작·종료, 에이전트 시작·단계·종료에 반응한다. 파일 도착이나 웹훅 내용에는 반응하지 않는다. 11-18의 D08(조회 직전 동기화)이 맞는 선택이었음을 뒷받침한다. 이 사실은 소스의 설명문을 읽어 얻었고 동작을 시험하지는 않았다.
4. **Hermes의 `project` 기능은 프로젝트 사이의 순서를 모른다.** 세션을 묶고 칸반 보드를 연결하는 용도이다. 연결 정보는 따로 만들어야 한다.
5. **testgate는 이미 이번 분석 대상의 축소본을 만든다.** `reduced_context()`가 확인된 파일과 제외된 파일을 뺀 diff를 만든다. 다만 기존 코드는 참고 문서를 축소본이 아니라 전체 맥락으로 불렀다. D39에서 이 점을 고쳤다.

## 3. 결정 기록

### D29 '알맞은 순번'의 뜻

- 사용자 요구: 두 프로젝트가 "항상 연동된 상태"이거나 서로를 "언급하는 상태"가 되는 것은 피하고 싶다.
- "정확히 알맞은 순번, 의도대로"라는 표현은 사용자가 직전 메시지에서 쓴 문장이다. To-do 9번에는 그 문장을 문체만 다듬어 옮겼다.
- 제안한 해석을 사용자가 확인했다. **순번** = 데이터가 흐르는 순서(PR이 오면 CED 해설을 먼저 만들고, 그 결과를 분석이 받는다). **의도** = 각 프로젝트가 자기 목적대로만 쓰인다. **방식** = 서로 직접 모르고 Hermes 쪽 설정이 순서를 정한다.
- 제외한 해석: 여러 프로젝트 중 무엇을 부를지 고르는 일(라우팅). 프로젝트가 늘어난 뒤에 필요하다.

### D30 연결 위치

- 선택지: testgate에 범용 공급자 자리, 연결은 설정(권장) / Hermes 쪽 중립 연결 정의 파일 / Hermes LLM이 안내 문서를 보고 판단
- 선택: 첫째.
- 이유: 가장 작은 변경이다. testgate는 "공급자 명령을 설정으로 지정할 수 있다"는 범용 자리만 갖는다. ced-taker는 그 계약을 지키는 명령일 뿐이다.
- 기각한 것: 중립 연결 정의 파일은 새로 만들 것이 많고 Hermes가 그것을 읽는 방법도 필요하다. LLM 판단은 토큰이 들고, 분석 경로에 Hermes 세션이 없어서 사실상 작동하지 않는다.
- 되돌리면: 중립 연결 정의로 옮기려면 testgate의 설정 읽기를 그쪽으로 바꾸면 된다. 계약(5장)은 그대로 쓸 수 있다.

### D31 대화 경로

- 선택: 지금은 분석 경로만.
- 이유: 대화 경로(Discord 등)에서 CED를 쓰려면 훅으로 맥락을 넣어야 하고, Hermes 세션 토큰이 든다. 토큰을 쓰지 않는 방향과 맞지 않는다.
- 미착수: 필요해지면 따로 설계한다.

### D32 이번 단계의 산출물 (권장안과 다름)

- 선택지: 설계 문서만(권장) / 설계 문서 + ced-taker 쪽 공급자 명령 / 설계 문서 + 두 프로젝트 모두 구현
- 선택: 셋째. 사용자는 구현의 주요 세부는 다시 질문하며 진행하라고 강하게 요청했다.
- 결과: ced-taker와 testgate를 모두 고쳤다. testgate는 별도 브랜치(`feat/context-providers`)에 두고 병합하지 않았다. testgate 설치본과 라이브 설정은 건드리지 않았다.

### D33 독립성 원칙

사용자 요구: 이 프로젝트는 "독립적 기능"의 생태로 동작해야 한다. 한쪽 프로젝트가 없어도 잘 동작해야 한다.

이 원칙을 다음 네 가지로 구체화하고 시험으로 지켰다.

1. 공급자를 설정하지 않으면 testgate는 이전과 똑같이 동작한다. 기존 239개 시험이 그대로 통과한다.
2. ced-taker는 단독으로 동작한다. `sync`, `explain`, `provide`가 모두 testgate 없이 돈다.
3. 코드가 서로를 부르지 않는다. 양쪽 소스 코드에서 상대 이름을 검색한 결과가 없다.
4. testgate의 시험은 가짜 공급자로 한다. ced-taker 없이 시험이 통과한다.

### D34 연결 형식

- 선택지: 명령 실행 + JSON 입출력(권장) / Python 모듈 직접 호출 / 로컬 HTTP 서비스
- 선택: 첫째. 언어에 무관하고 서로의 코드를 불러오지 않는다.
- 사용자의 질문: SQLite를 쓰는데 Git에 공개하고 관리해도 되는가, 연결에 어떤 영향을 주는가?
- 답: DB 파일은 저장소에 없고(기본 위치는 Hermes 폴더), 공개되는 것은 코드와 표 구조뿐이다. 연결에는 영향이 없다. DB는 ced-taker 내부의 캐시이고, testgate는 JSON만 본다. 운영상 달라지는 점은 (1) 첫 실행에서 DB를 만드는 지연이 한 번 있고(측정하지 않음), (2) 분석이 겹쳐도 WAL 모드라 서로 막지 않으며, (3) DB는 지워도 볼트에서 복원되지만 놓침 기록과 이력은 사라진다는 것이다.

### D35 저장소와 제품의 연결

- 선택: ced-taker 로컬 설정에서 매핑(권장). testgate는 저장소 이름(`owner/name`)만 넘기고 "제품"이라는 개념을 모른다.
- 설정 위치: ced-taker의 `local/config.json`의 `repos`. 저장소 이름은 대소문자를 구분하지 않는다.

### D36 공급자 실패 시

- 선택: 해설 없이 분석을 계속하고, 보고서에 한 줄을 남긴다(권장).
- 사용자 의견: 프로젝트가 분리돼 있으니 testgate는 "CED가 개입했다"를 알아서 알게 하되 독립성을 계속 지켜야 한다.
- 반영: testgate 코드에는 "CED"라는 말이 없다. 보고서의 "비고"에는 일반적인 문구가 나온다.
  - 성공: `참고 문서 N건이 첨부됨 (공급자: 이름표): 제목들`. "CED 해설"이라는 글자는 공급자가 준 제목에만 나타난다.
  - 실패: `참고 문서 공급자(이름표)가 응답하지 않아 해설 없이 분석함 (사유 코드).`
- 사유 코드: `timeout`, `exit_code`, `bad_output`, `unsupported_version`, `output_too_large`, `not_found`, `not_runnable`. 공급자가 쓴 오류 문장은 보고서에 넣지 않는다(로그에만 남는다).

### D37 DB 파일 Git 제외

- 선택: `.gitignore`에 `*.db`, `*.db-wal`, `*.db-shm`, `*.sqlite*`를 추가한다(권장). DB 안에 CED 본문이 있으므로, 위치를 저장소 안으로 잘못 지정해도 커밋되지 않게 하는 안전망이다.

### D38 서로의 이름 언급 (권장안과 다름)

- 선택지: 코드와 사용자 문서에는 없음, 설계 기록에는 허용(권장) / 어디에도 없음 / 제한 없음
- 선택: 제한 없음.
- 주의: 이것은 문서와 주석의 이름 언급에 관한 결정이다. 코드가 서로를 부르지 않는다는 D33의 기능적 독립과는 별개이다. 구현은 두 가지를 모두 지켰다. 이름 언급이 코드에서 필요하지 않았기 때문이다.

## 4. 구조

```
testgate (소비자)                              ced-taker (공급자)
  testgate.json                                 local/config.json
   analysis.context_providers: [                  vault: (볼트 위치)
     {label, command, timeout_seconds}, ...]      repos: {"owner/name": "제품"}
  분석 직전, 목록 순서대로 명령 실행
    stdin  ← {version, repo, title, description, diff}
    stdout → {version, docs: [{id,title,text}], notices: [...]}
  명령이 없거나 실패 → 해설 없이 계속, 보고서 "비고"에 한 줄
```

연결은 설정의 명령줄 한 줄이다. 어느 쪽 코드도 상대를 모른다.

## 5. 계약 명세 (버전 1)

공급자 프로그램이 지킬 것이다. 어떤 프로그램이든 이것만 지키면 testgate의 공급자가 될 수 있다.

**호출**: 설정의 `command`(인자 목록)를 셸 없이 실행한다. 표준 입력에 요청을 주고 표준 출력에서 응답을 읽는다.

**요청** (표준 입력, JSON, UTF-8)

| 필드 | 형식 | 설명 |
|---|---|---|
| `version` | 정수 | 1 |
| `repo` | 문자열 | `owner/name` |
| `title` | 문자열 | PR 제목. 없으면 빈 문자열 |
| `description` | 문자열 | PR 설명. 없으면 빈 문자열 |
| `diff` | 문자열 | unified diff. 이번에 분석하는 파일만 들어 있다. |

**응답** (표준 출력, JSON, UTF-8, 한 줄이면 충분)

| 필드 | 형식 | 설명 |
|---|---|---|
| `version` | 정수 | 1 |
| `docs` | 배열 | `{id, title, text}` 문자열 세 개. 비어 있으면 첨부할 문서 없음 |
| `notices` | 배열(선택) | 보고서 비고에 남길 짧은 글 |

**실패**: 종료 코드가 0이 아니면 실패이다. 표준 오류에는 사유 코드만 쓴다(본문과 경로는 쓰지 않는다). 표준 출력에는 JSON만 쓴다.

**호출하는 쪽의 보장과 제한**

- 공급자 프로세스에는 환경 변수 `PATH`, `HOME`, `HERMES_HOME`, `LANG`, `LC_ALL`, `TZ`만 넘긴다. 서명 키 같은 비밀은 넘기지 않는다.
- 제한: 시간 20초(설정으로 바꿈), 출력 2 MiB, 문서 50건, 문서당 2만 자, 합계 6만 자, 안내 5건(각 300자).
- 문서는 신뢰하지 않는 데이터 블록으로 프롬프트에 들어가고, 지시로 읽지 않는다.
- 보고서에는 제목과 안내만 나온다. 보고서의 이스케이프(멘션, HTML, 이미지·링크 문법)를 거치고, 맨 URL은 자동 링크가 되지 않게 깨뜨린다.
- 알 수 없는 필드는 무시한다. 버전이 다르면(`version != 1`) 실패로 본다.

**ced-taker의 공급자 동작**

- 저장소가 어떤 제품에도 연결돼 있지 않으면 볼트와 DB를 열지 않고 `{"version":1,"docs":[],"notices":[]}`를 돌려준다.
- 연결된 제품의 폴더가 없으면 빈 문서와 안내 한 줄을 돌려준다.
- 문서 ID는 `ced:<컬럼명>`이고, 요약 문서의 ID는 `ced-summary`이다. 컬럼명이 `summary`인 경우와 충돌하지 않게 접두어를 붙였다.
- 동기화 문제(상태 파일 오류, 해시 불일치 등)가 있으면 해설이 없어도 `notices`로 알린다.

## 7. 설정 방법 (로컬에서만 한다)

아래는 사용자가 직접 할 일이다. 이 저장소에는 개인 경로를 적지 않는다. 경로는 예시이다.

1. **ced-taker**: `local/config.json`(Git 제외)에 볼트와 저장소-제품 연결을 적는다.
   ```json
   {"vault": "<볼트 폴더>", "repos": {"owner/name": "제품 A"}}
   ```
2. **testgate**: `testgate.json`의 `analysis`에 공급자를 적는다.
   ```json
   "context_providers": [
     {"label": "사전", "command": ["<ced-taker 저장소>/bin/ced-taker", "provide"]}
   ]
   ```
3. **testgate 설치본 갱신**: testgate의 변경을 병합한 뒤 `scripts/install.sh`를 다시 실행한다. 설치본(`$HERMES_HOME/testgate/lib`)이 사본이라서 이 단계가 없으면 반영되지 않는다.

## 8. 검증과 발견한 문제

**한 검증**

- ced-taker: 단위 시험 198개 통과(공급자 계약, 설정 매핑, 실행 파일을 실제 프로세스로 띄우는 시험 포함).
- testgate: 단위 시험 286개 통과(기존 239개 + 새 47개).
- **끝에서 끝까지**: 실제 ced-taker와 실제 볼트를 testgate의 공급자 자리에 끼워 확인했다. (1) 연결된 저장소에서 문서 1건이 첨부되고 비고가 남았다. (2) 연결 없는 저장소는 빈 결과였다. (3) 공급자가 없는 설정은 문서가 없었다. (4) 고장 난 명령은 사유 코드 한 줄이 남고 분석이 이어졌다. (5) 고장과 정상 공급자를 함께 놓아도 정상 쪽 문서가 붙었다. 임시 설정으로 했고, 라이브 설정과 설치본은 건드리지 않았다.
- **독립성**: 양쪽 소스 코드에서 상대 이름을 검색한 결과가 없다.
- **변이 시험**: 보호 장치를 일부러 깨 보고 시험이 실패하는지 확인했다. ced-taker는 "연결 없는 저장소는 DB를 열지 않는다"와 "문서 ID 접두어", testgate는 "환경 변수 최소화", "분석 대상만 전달", "보고서 안내", "공급자 실패를 잡아 분석 계속", "맨 URL 깨뜨리기"이다.

**발견한 문제**

- **시험이 실제 홈 폴더에 DB를 만들었다.** 변이 시험 중 환경 변수 없이 실행된 코드가 실제 Hermes 폴더에 빈 DB를 만들었다. 즉시 지웠고(행 0개), 시험 환경이 실제 홈을 가리킬 수 있었다는 구멍을 막았다. 모든 공급자 시험이 `HERMES_HOME`을 임시 폴더로 바꾸고, 시험이 끝난 뒤 실제 홈에 `ced-taker` 폴더가 생겼으면 실패하는 보호 시험(`test_zz_real_home_guard.py`)을 넣었다.
- **한글 바로 뒤의 URL**: URL을 깨뜨리는 정규식이 단어 경계(`\b`)에 의존해서 `클릭http://…`를 놓쳤다. 한글과 영문 사이에는 단어 경계가 없기 때문이다. 경계 조건을 뺐다.
- **보고서 이스케이프와의 중복**: I9 참고.
- **시험 불안정(미해결)**: testgate의 기존 시험 `FilterSpoolTest`가 전체 시험을 반복할 때 드물게 임시 폴더 정리에서 `Directory not empty`로 실패한다. 이 브랜치에서는 약 20회 중 3회였고, 수정 전 `main`에서는 전체 13회와 단독 65회에서 0회였다. 필터가 백그라운드로 띄운 실행기가 파일을 쓰는 동안 정리가 겹치는 것으로 추정하지만, 의도적으로 재현하지 못했다. 이 브랜치가 빈도를 키웠는지 우연인지 가리지 못했다. 시험은 고치지 않았다.
- **막다른 시도**: 보호 시험을 `tests/__init__.py`의 `load_tests`로 넣으려다, 그것이 하위 시험의 탐색을 대체해서 시험 1개만 도는 것을 발견하고 별도 파일로 바꿨다.
